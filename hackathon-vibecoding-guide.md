# Подготовка команды к хакатону по вайбкодингу

## Исходные условия

Команда участвует в двухчасовом хакатоне, вероятная тема — HR-системы.

Участники:

- Алиса — самостоятельно проектирует и реализует назначенную часть продукта;
- Костя — самостоятельно проектирует и реализует назначенную часть продукта;
- тренер — помогает удаленно, но не пишет основную реализацию.

Главная цель — за ограниченное время показать не production-систему, а убедительный прототип с понятной бизнес-ценностью, цельным пользовательским сценарием и сильной демонстрацией.

## Оценка первоначальной идеи

Идея в основе правильная: для двухчасового хакатона важнее хорошо показать решение реальной пользовательской проблемы, чем строить сложную архитектуру и лишнюю инфраструктуру.

Команда сознательно решила делать полноценный backend, PostgreSQL и Docker/Docker Compose — это увеличивает риск интеграции и подготовки, поэтому окружение должно быть полностью готово (см. [Makefile](#makefile-для-локальной-разработки)) до старта хакатона, а рабочий процесс необходимо сделать жестче и проще.

### Основные риски

1. **Слишком длинное интервью с Claude.**

   Claude легко задаст 15–20 полезных вопросов, после чего на реализацию останется слишком мало времени. Следует разрешить один пакет максимум из пяти важных вопросов. Все некритичные решения агент принимает самостоятельно.

2. **Разделение по слоям (frontend/backend) вместо разделения по фичам.**

   Если один участник целиком делает backend, а другой — целиком frontend, фронту нечего показывать, пока не готов бэк: это создает взаимные ожидания, простой и позднюю интеграцию. Даже при полноценном backend и БД делить работу нужно вертикально — по фичам (каждая фича включает свой эндпоинт API, свои типы и свой UI), а не горизонтально по слоям. Лучше назначить одного участника владельцем основного пользовательского сценария и интеграции, а второму поручить независимую эффектную фичу целиком, со своим API-контрактом и своим UI, с четким входом и выходом.

3. **Слишком свободная постановка UI/UX.**

   Если просто попросить сделать красивую HR-систему, велик риск получить типовой дашборд. Агенту можно доверить визуальные и технические решения, но необходимо заранее определить:

   - конкретного пользователя;
   - болезненную ситуацию;
   - решение, которое принимает пользователь;
   - результат этого решения;
   - один wow-момент демонстрации.

4. **Один общий сеанс Claude Code.**

   Источником истины должны быть Git и `HACKATHON.md`, а не история общей сессии. У каждого участника должна быть собственная сессия и собственная ветка. Если работа идет на одном компьютере, следует использовать Git worktree. См. [документацию о сессиях Claude Code](https://code.claude.com/docs/en/how-claude-code-works).

5. **Избыточное использование subagents и параллельных AI-процессов.**

   Они быстрее расходуют квоту и генерируют больше кода, который необходимо проверять и интегрировать. Ограничение Claude — это динамическая квота в пятитчасовом окне, а не пять часов гарантированной работы. Расход зависит от модели, размера репозитория, длины контекста и использования инструментов. См. [описание ограничений Claude Code](https://support.anthropic.com/en/articles/11145838-using-claude-code-with-your-max-plan).

6. **Слишком подробный трекер.**

   Для двух часов достаточно двух крупных задач с ответственными, принадлежащими им файлами и критериями готовности. После разделения работ `HACKATHON.md` становится read-only, чтобы оба участника не получили конфликт в одном файле.

7. **Добавление функций до последней минуты.**

   Примерно за 30 минут до завершения необходим feature freeze. Оставшееся время тратится только на интеграцию, исправление ошибок, визуальную полировку и репетицию показа.

## Рекомендуемая организация работы

```text
Задание
   │
   ▼
5 бизнес-вопросов → HACKATHON.md
   │
   ├── Участник-интегратор: основной сценарий
   │
   └── Участник-фича-оунер: независимый wow-модуль
                         │
                         ▼
                раннее слияние и проверка
                         │
                         ▼
              полировка → демонстрация
```

### Роли

Роль интегратора получает тот, кто увереннее работает с Git и быстрее принимает технические решения. Он владеет:

- оболочкой frontend-приложения (маршрутизация, глобальные стили);
- основным пользовательским сценарием и его фичей целиком (эндпоинт API, типы, UI);
- общей структурой backend (точка входа, общие модели БД, `docker-compose.yml`, `Makefile`);
- финальной сборкой и запуском всего стека.

Второй участник создает независимую фичу целиком — свой эндпоинт API, свои типы и свой UI, например:

- ранжирование кандидатов;
- анализ причин текучести;
- карьерный план сотрудника;
- помощник руководителя;
- анализ обратной связи;
- визуализация командных рисков.

Этот участник не редактирует общий `App`, роутер, глобальные стили, `package.json`, точку входа backend, общие модели БД и `docker-compose.yml`. Он работает только в своей папке фичи (свой роут/модуль API, свои типы, свой feature-модуль на фронте) и передает интегратору готовую фичу — которая уже подключена, см. «Швы» ниже.

### Швы: как разделить без конфликтов при merge

Чтобы фичи не сталкивались на одних и тех же строках одного файла, планирующая сессия (до разделения работ) сама пишет и коммитит «швы» — точки подключения обеих фич, уже вставленные в приложение:

- `backend/app/models.py` — все сущности сразу, одним файлом;
- `backend/scripts/seed.py` — реалистичные демоданные сразу во все таблицы, которые нужны обеим фичам;
- `backend/app/main.py` — `include_router` для обеих фич уже прописан, роутеры внутри — пустые заглушки;
- `frontend/src/router.tsx` — оба маршрута уже заведены, экраны — пустые заглушки.

После этого коммита `main.py`, `router.tsx`, `models.py`, `docker-compose.yaml` и `Makefile` не меняет никто до конца хакатона — участники дальше правят только файлы внутри своей папки фичи.

Оба участника читают демоданные из общего `seed.py`, а не результат работы друг друга: если фича Б показывает то, что создает фича А, владелец Б простаивает, пока не готова А. Фичи связаны только в сценарии показа (пользователь переходит с одного экрана на другой), не в данных.

Схема БД не мигрируется через Alembic — на двухчасовой хакатон это лишний риск конфликта веток (две ветки от одного `down_revision` → после merge два head'а → `alembic upgrade head` падает). Схема фиксируется один раз в замороженном `models.py`; смена схемы — это `make reset-data` (пересоздать БД из моделей + `seed.py`), а не миграция.

### Рабочий ритм на два часа

- **0–10 минут:** понять задание, пользователя и главную боль.
- **10–25 минут:** получить от Claude короткую спецификацию, разделение по фичам и закоммитить швы (модели, seed, пустые роутеры/маршруты).
- **25–65 минут:** параллельно собрать первые рабочие варианты.
- **К 45-й минуте:** у каждого должен быть первый запускаемый commit.
- **65–85 минут:** объединить части и пройти сценарий целиком.
- **После 85-й минуты:** feature freeze — запретить новые крупные функции.
- **Оставшееся время:** исправления, визуальная полировка, хорошие демоданные и репетиция питча.

## Принцип выбора продукта

Лучше реализовать один ясный путь:

> HR-специалист увидел проблему → система объяснила ее → предложила действие → показала ожидаемый результат.

Это сильнее, чем пять разрозненных экранов без законченного сценария.

Минимальная формула идеи:

```text
Конкретный пользователь
    + болезненная ситуация
    + одно важное решение
    + наглядный результат
    + один wow-момент
```

## Что подготовить заранее

Рекомендуемый минимальный шаблон:

- React + TypeScript + Vite на frontend;
- backend на FastAPI (Python) с реальным API;
- PostgreSQL как единственная БД;
- один `docker-compose.yaml` в корне репозитория (без вложенных `infra/`-путей) поднимает БД и backend; frontend запускается локально (`npm run dev`) для быстрой правки и отладки — см. [Makefile](#makefile-для-локальной-разработки);
- готовая дизайн-система и базовые компоненты на фронте;
- адаптивная оболочка приложения;
- на фронте каждая фича сама обращается к настоящему backend API (без общего слоя `services`), но с возможностью подставить моковые данные как fallback, если backend в моменте недоступен;
- `Makefile` с командами `make dev`, `make build`, `make lint`, `make test`, `make check`, `make reset-data` (см. пример ниже);
- `.env.example` без секретов;
- деление на backend и frontend по фичам с доменными именами папок (`features/<домен>/`, не по владельцу), см. [«Швы»](#швы-как-разделить-без-конфликтов-при-merge) и [структуру каталогов](#структура-каталогов);
- кнопка сброса демонстрационных данных = `make reset-data` (пересоздать БД из моделей + seed, либо очистка `localStorage`-fallback);
- без Alembic/миграций — схема фиксируется один раз в `models.py`, без обязательной авторизации и без микросервисов — один backend-сервис на всю систему.

Если продукт использует внешний AI API, необходимо предусмотреть детерминированный fallback с заранее подготовленным результатом. Демонстрация не должна зависеть от сети, лимита API или случайного ответа модели.

В репозитории установлен project-level скилл `frontend-design` (`.claude/skills/frontend-design/`, источник — [anthropics/skills](https://github.com/anthropics/skills/blob/main/skills/frontend-design/SKILL.md)). Его стоит вызывать при работе над визуальным дизайном шаблона и фич, чтобы интерфейс не выглядел типовым AI-дашбордом.

### Структура каталогов

Папки фич называются по домену (`ranking/`, `turnover/`), а не по владельцу (`alice/`, `kostya/`) — владелец фиксируется в `HACKATHON.md`, а не в пути. Каждая папка фичи самодостаточна: свои типы, свой доступ к API, свои моки, свой UI — общего `contracts/` и общего `services/` нет, чтобы не было файла, который правят оба участника.

```text
backend/app/
  main.py, db.py, config.py    заморожено (роутеры обеих фич уже подключены)
  models.py                    заморожено (все сущности сразу)
  features/ranking/            один владелец: router.py, schemas.py
  features/turnover/           один владелец: router.py, schemas.py
backend/scripts/seed.py        заморожено (демоданные сразу во все таблицы)

frontend/src/
  App.tsx, router.tsx          заморожено (оба маршрута заведены заранее)
  shared/ui/                   заморожено: берем что есть, не выносим новое
  shared/http.ts               заморожено: fetch + переключатель моков
  features/ranking/            один владелец: ui.tsx, api.ts, types.ts, mocks.ts
  features/turnover/           один владелец: ui.tsx, api.ts, types.ts, mocks.ts
```

Если во время хакатона нужен компонент, которого нет в `shared/ui/`, — его делают внутри своей папки фичи и не выносят наверх до конца хакатона: дублирование на таком масштабе дешевле, чем согласование правок в общем файле.

Pydantic-схемы на backend и TS-типы на фронте описывают одни и те же поля руками, без кодогенерации из OpenAPI — настройка генератора для двух фич не окупается.

## Makefile для локальной разработки

Postgres и backend (FastAPI) поднимаются в Docker через один `docker-compose.yaml` в корне репозитория, а frontend запускается локально командой `npm run dev` — так быстрее смотреть результат и чинить ошибки, чем гонять весь стек в контейнерах. Файл `Makefile` уже лежит в корне репозитория; команды под капотом (`pip`, `ruff`, `pytest`) соответствуют выбранному стеку backend — FastAPI/Python. Миграций (Alembic) сознательно нет — схема одна и зафиксирована в замороженном `models.py`, `make seed`/`make reset-data` создают таблицы и наполняют их напрямую.

```makefile
# Hackathon prototype — dev commands. See CLAUDE.MD and hackathon-vibecoding-guide.md.
.DEFAULT_GOAL := help
BACKEND := backend
FRONTEND := frontend
# Один docker-compose.yaml в корне репозитория — docker compose находит его
# без -f. Переменные окружения (POSTGRES_USER и т.д.) берутся из .env рядом.
COMPOSE := docker compose

help: ## список команд
	@grep -E '^[a-zA-Z_-]+:.*?## .*$$' $(MAKEFILE_LIST) | \
	  awk 'BEGIN{FS=":.*?## "}{printf "  %-14s %s\n", $$1, $$2}'

db-up: ## поднять postgres (docker)
	$(COMPOSE) up -d db

back-up: ## поднять postgres + backend (docker, пересборка по кешу) + накатить схему и демоданные
	$(COMPOSE) up -d --wait --build db backend
	$(MAKE) seed

build: ## пересобрать образ backend
	$(COMPOSE) build backend

down: ## остановить все контейнеры
	$(COMPOSE) down

logs: ## логи backend
	$(COMPOSE) logs -f backend

install: ## поставить зависимости back+front
	cd $(BACKEND) && python -m pip install -e ".[dev]"
	cd $(FRONTEND) && npm install

seed: ## создать таблицы (если их нет) и залить демо-данные — идемпотентно
	$(COMPOSE) exec -T backend python -m scripts.seed

dev: back-up ## db+backend в docker + frontend локально (vite)
	cd $(FRONTEND) && { [ -d node_modules ] || npm install; } && npm run dev

dev-build: ## то же, что dev, но с пересборкой образа backend без кеша
	$(COMPOSE) build --no-cache backend
	$(MAKE) dev

test: ## все тесты
	cd $(BACKEND) && pytest -q
	cd $(FRONTEND) && npm run test

lint: ## линт + формат + типы
	cd $(BACKEND) && ruff format --check . && ruff check .
	cd $(FRONTEND) && npm run lint

check: test lint ## ВОРОТА КАЧЕСТВА: тесты + линт. Гонять после каждой фичи.

fmt: ## автоформат
	cd $(BACKEND) && ruff format . && ruff check --fix .
	cd $(FRONTEND) && npm run fmt

reset-data: ## сброс демоданных: снести volume БД и поднять стек заново (кнопка "сбросить демо")
	$(COMPOSE) down -v
	$(MAKE) back-up

.PHONY: help db-up back-up build down logs install seed dev dev-build test lint check fmt reset-data
```

По сравнению с более тяжелым production-примером (несколько воркеров, отдельная заглушка эмбеддингов, деплой на выделенный сервер по SSH) здесь сознательно нет: очередей/воркеров, staging/prod-деплоя, отдельных профилей compose — для двухчасового хакатона это лишняя инфраструктура. Если во время хакатона понадобится реальный деплой демо, его добавляет интегратор отдельной целью `deploy` по аналогии, а не потому что она «нужна на всякий случай».

### Проверка готовности участников

До хакатона Алиса и Костя отдельно проверяют:

- клонирование репозитория;
- установку зависимостей;
- запуск приложения;
- создание ветки;
- commit, push, pull и merge;
- доступ к Claude Code;
- команды `/status`, `/model`, `/clear`;
- отсутствие настоящих персональных данных в демоданных.

## Промпт для подготовки среды

Перед хакатоном этот промпт можно передать Claude Code в подготовленном репозитории:

```text
Подготовь этот репозиторий как легкий шаблон для двухчасового хакатона
по вайбкодингу. Конкретная тема задания пока неизвестна, вероятное
направление — HR-системы.

Сначала изучи состояние репозитория. Затем создай минимальную,
быстро изменяемую основу прототипа.

Требования:
- Frontend: React, TypeScript и Vite.
- Backend: FastAPI (Python) с реальным API.
- База данных: PostgreSQL, без альтернатив и без ORM-абстракций
  «на будущее».
- Весь проект (БД + backend) контейнеризируй через один `docker-compose.yaml`
  в корне репозитория, без лишних вложенных путей и без лишних сервисов.
  Frontend в контейнер не заворачивай — он должен запускаться локально
  командой вида `npm run dev`, чтобы было быстрее смотреть результат и
  чинить ошибки.
- Сделай `Makefile` с командами вида `make dev` (поднять БД+backend в
  Docker и frontend локально), `make db-up`, `make back-up`, `make down`,
  `make install`, `make seed`, `make reset-data`,
  `make test`, `make lint`, `make check`, `make fmt` — по образцу раздела
  [Makefile для локальной разработки](#makefile-для-локальной-разработки).
  Без Alembic/миграций: схема БД описывается один раз в `models.py`,
  таблицы создаются через `Base.metadata.create_all()` при засеивании.
- Современный, выразительный, но нейтральный B2B-интерфейс.
- Готовые компоненты: layout, sidebar/header, карточки, таблица,
  форма, modal/drawer, toast, loading, empty и error state.
- Каждая фича на фронте сама обращается к настоящему backend API (без
  общего слоя services); предусмотри локальный fallback на моковые
  данные на случай, если backend в моменте недоступен (например, для
  полировки UI).
- Заведи «швы» — точки подключения обеих будущих фич, уже вставленные
  в приложение и подключенные (`include_router` в `main.py` с двумя
  пустыми роутерами-заглушками на backend, два маршрута с пустыми
  экранами в роутере на frontend), чтобы дальше эти общие файлы никто
  не трогал. Папки фич называй по домену (`features/<домен>/`), не по
  владельцу — см. [структуру каталогов](#структура-каталогов).
- Разделение задач между двумя разработчиками — по фичам (каждая фича
  вертикальна: свой эндпоинт API + свои типы + UI), а не по слоям
  frontend/backend: фронту нельзя ждать, пока бэк доделает всё подряд.
- Подготовь .env.example (в т.ч. для БД), но не добавляй секреты.
- Добавь несколько синтетических HR-сущностей в `models.py` и общий
  `seed.py`, который наполняет демоданными все таблицы сразу (обе
  будущие фичи должны читать из него, а не друг из друга), не
  реализуя конкретный продукт.
- Не добавляй авторизацию, сложный state management, CI/CD и другие
  production-механизмы сверх того, что перечислено выше.
- Не используй внешнюю сеть во время основной демонстрации.
- Все видимые элементы шаблона должны работать; никаких мертвых кнопок.
- Создай короткий README с командами запуска (через Makefile).
- Создай краткий CLAUDE.md по правилам ниже.
- Запусти lint и production build (frontend и backend) и исправь
  найденные проблемы.

Главные качества шаблона: быстрый старт, визуальный эффект,
простота изменений и минимальный риск интеграционных конфликтов,
несмотря на наличие полноценного backend, БД и Docker.
Не переусложняй архитектуру сверх необходимого.
```

## Рекомендуемый `CLAUDE.md`

`CLAUDE.md` — это короткая постоянная конституция репозитория, а не место для конкретного задания хакатона. Anthropic рекомендует оставлять в нем только правила, которые применяются к каждой сессии: раздутые инструкции занимают контекст и хуже соблюдаются. См. [рекомендации Anthropic](https://code.claude.com/docs/en/best-practices).

```md
# Hackathon mode

Это репозиторий прототипа для двухчасового хакатона.

## Приоритеты

1. Понятная ценность для конкретного пользователя.
2. Полностью работающий демонстрационный сценарий.
3. Визуальная убедительность и хорошие демоданные.
4. Надежность запуска.
5. Только затем — техническая чистота.

## Правила реализации

- Перед работой прочитай `HACKATHON.md`.
- Реализуй только задачу и файлы, назначенные текущему участнику; делить работу — по фичам, а не по слоям frontend/backend.
- Не изменяй файлы другого участника без явной договоренности.
- Не редактируй `HACKATHON.md` после начала параллельной работы.
- Самостоятельно принимай некритичные решения по UI/UX и реализации.
- Задавай вопрос только тогда, когда ответ существенно меняет продукт.
- Backend, PostgreSQL и Docker/Docker Compose — часть согласованного стека; frontend на моковых данных/localStorage используй только как временный fallback, если backend в моменте недоступен.
- Не добавляй авторизацию, лишние сервисы, БД или инфраструктуру сверх согласованного стека (backend + PostgreSQL + Docker Compose), если без них можно показать пользовательскую ценность.
- Не делай больших рефакторингов и не меняй стек во время хакатона.
- Не запускай subagents и другие параллельные AI-процессы.
- Все видимые кнопки должны работать либо быть удалены.
- Для внешних AI/API-функций делай демонстрационный fallback.
- Не используй настоящие персональные данные.

## Завершение задачи

- Пройди назначенный пользовательский сценарий.
- Запусти lint и build.
- Проверь интерфейс в браузере.
- Сообщи измененные файлы, результат проверок и известные ограничения.
- Сделай небольшой осмысленный commit, но не сливай чужую ветку самостоятельно.
```

## Главный промпт после получения задания

Этот промпт запускает один из участников в отдельной короткой planning-сессии:

```text
Мы участвуем в двухчасовом хакатоне по вайбкодингу.

Участники:
- Алиса;
- Костя;
- тренер помогает только удаленно и не пишет основную реализацию.

Вот исходное задание хакатона:

<ВСТАВИТЬ ЗАДАНИЕ>

Вот наша предварительная идея:

<ВСТАВИТЬ ИДЕЮ>

Сейчас не пиши код.

Сначала задай нам одним сообщением не более пяти вопросов.
Спрашивай только то, что существенно влияет на:
- целевого пользователя и его боль;
- главное действие пользователя;
- критерии жюри;
- входные данные и ожидаемый результат;
- сильные стороны Алисы и Кости.

После ответов:
1. Критически оцени идею.
2. Если она слишком большая, сократи ее до одного сильного сценария.
3. Сам выбери разумные UI/UX и технические решения.
4. Создай один файл `HACKATHON.md` не длиннее 120 строк.
5. Заведи и закоммить «швы»: `backend/app/models.py` со всеми сущностями,
   `backend/scripts/seed.py` с демоданными во все таблицы, `main.py` с
   `include_router` для обеих будущих фич на пустых роутерах-заглушках,
   `router.tsx` с обоими маршрутами на пустых экранах-заглушках. После
   этого коммита `models.py`, `seed.py`, `main.py`, `router.tsx`,
   `docker-compose.yaml` и `Makefile` не меняются до конца хакатона.
6. Дальше реализацию не начинай — её делают Алиса и Костя каждый в своей сессии.

В `HACKATHON.md` должны быть:
- проблема и конкретный пользователь;
- ценностное предложение одним предложением;
- основной сценарий демонстрации длительностью не более 90 секунд;
- один wow-момент;
- что сознательно не делаем;
- ключевые сущности или контракт между двумя частями;
- задача Алисы;
- задача Кости;
- принадлежащие каждому каталоги и файлы;
- критерии готовности каждой задачи;
- порядок интеграции;
- общий критерий готовности продукта;
- короткий план презентации.

Раздели работу так, чтобы:
- один участник владел основным сценарием и финальной интеграцией;
- второй создавал независимый feature-модуль (со своим API-эндпоинтом,
  своими типами и своим UI) в отдельной папке по домену, а не по имени
  участника (например `features/turnover/`, а не `features/kostya/`);
- деление было по фичам (вертикально: эндпоинт + типы + UI), а не по
  слоям frontend/backend — иначе фронту придется ждать бэк;
- они не редактировали одни и те же файлы (`docker-compose.yaml`,
  `Makefile`, общие `models.py`, `main.py`, `router.tsx` — эти файлы уже
  зафиксированы как «швы» на шаге 5 выше);
- первая рабочая версия каждой части могла появиться примерно за 35 минут;
- обе части читали демоданные из общего `seed.py`, а не результат работы
  друг друга — чтобы не ждать, пока другая фича начнет создавать данные.

Не дроби работу на мелкие технические подзадачи.
На каждого участника должно быть не более пяти пунктов.
Не добавляй идеи «на будущее».
Если информации не хватает, явно сделай разумное предположение.
```

## Промпт для каждого участника

После того как `HACKATHON.md` создан, закоммичен и получен обоими участниками, каждый запускает собственную рабочую сессию:

```text
Прочитай `CLAUDE.md` и `HACKATHON.md`.

Я — <АЛИСА ИЛИ КОСТЯ>. Реализуй только назначенную мне часть.

Сначала коротко напиши:
- какой пользовательский результат я создаю;
- какие файлы буду изменять;
- какой интерфейс моя часть предоставляет второй части системы.

Если назначенные файлы пересекаются с областью другого участника,
остановись и сообщи о конфликте. В остальных случаях не задавай
уточняющих вопросов: самостоятельно принимай разумные решения
по реализации и UI/UX.

Сделай сначала минимальный работающий вертикальный сценарий (эндпоинт
API + типы + UI твоей фичи, читающий данные из общего `seed.py`), а
затем улучши его визуально. Не редактируй `models.py`, `main.py`,
`router.tsx`, `docker-compose.yaml` и `Makefile` — это зафиксированные
«швы». Не добавляй новую инфраструктуру, авторизацию или зависимости
сверх согласованного стека (FastAPI + PostgreSQL + Docker Compose) без
крайней необходимости.

После реализации:
- пройди сценарий в браузере;
- запусти lint и build;
- исправь ошибки;
- перечисли измененные файлы и ограничения;
- предложи короткое сообщение commit.

Не сливай ветки и не меняй область другого участника.
```

## Работа с Git

Минимальная схема:

1. Planning-сессия создает и коммитит `HACKATHON.md` в основную ветку.
2. Оба участника получают одинаковое состояние репозитория.
3. Алиса создает собственную ветку, например `alice/core-flow`.
4. Костя создает собственную ветку, например `kostya/wow-feature`.
5. Каждый делает небольшой первый commit как можно раньше.
6. Фича-оунер завершает независимый модуль и передает commit или ветку интегратору.
7. Интегратор объединяет изменения, запускает приложение, lint и build.
8. После feature freeze вносятся только исправления и визуальные улучшения.

Не следует одновременно менять:

- `package.json` (frontend) и файл зависимостей backend;
- главный файл frontend-приложения и точку входа backend;
- роутер (frontend) и общую конфигурацию API-роутов backend;
- глобальные стили;
- общие типы и общие/базовые модели БД;
- `docker-compose.yml` и `Makefile`;
- `HACKATHON.md`.

Если новый пакет или сервис в `docker-compose.yml` действительно нужен, его добавляет интегратор.

## Экономия лимита Claude Code

- Начать хакатон после обновления пятитчасового окна квоты.
- Если аккаунты отдельные, каждый работает со своей квотой.
- Использовать Sonnet как основную рабочую модель, если возможностей достаточно.
- Не запускать subagents и несколько фоновых сессий.
- Не просить Claude исследовать весь репозиторий без ограничения области.
- Не передавать длинные повторяющиеся описания — использовать `CLAUDE.md` и `HACKATHON.md`.
- Для планирования задать максимум пять вопросов одним сообщением.
- После двух неудачных исправлений использовать `/clear` и дать новый точный промпт.
- Не отправлять большие логи целиком; передавать только релевантный фрагмент.
- Следить за расходом через `/status` и контекстом через `/context`.

## Критерий готовности прототипа

Прототип готов, если:

- его можно запустить одной понятной командой;
- основной сценарий занимает не более 90 секунд;
- пользователь, проблема и результат понятны без объяснения архитектуры;
- данные выглядят реалистично, но не содержат персональной информации;
- все показанные элементы интерфейса работают;
- внешние API имеют fallback;
- после свежего запуска сценарий воспроизводится;
- lint и production build проходят;
- команда хотя бы один раз полностью отрепетировала демонстрацию.

## Финальный вывод

Оптимальная схема работы:

- одна короткая planning-сессия;
- один динамический файл `HACKATHON.md`;
- короткий постоянный `CLAUDE.md`;
- согласованный стек (backend + PostgreSQL + Docker/Docker Compose,
  frontend локально), готовый и проверенный заранее;
- две независимые рабочие сессии, деление задач по фичам, а не по
  слоям frontend/backend;
- один интегратор;
- один основной пользовательский сценарий;
- один wow-момент;
- ранний merge;
- запрет на новые функции в последние 30 минут.

Цель — не построить полноценную HR-платформу, а за 90 секунд убедительно показать, что конкретный пользователь получил полезный и измеримый результат.
